# Bug Report: GitHub Actions Windows Build Cannot Load Preset Selectable Petz

## 🐛 Bug Description
In the Windows x64 build artifact generated by the GitHub Actions CI/CD pipeline (`.\bin_buggy\LnzLive-Windows-x64\windows\PetzRendering.exe`), double-clicking any of the preset selectable `.lnz` pets under **Examples** (or **Local Storage**) in the left-hand `FileTree` panel fails to load the pet—neither the center 3D viewport (`DogGenerator`) nor the right-hand LNZ code editor (`LnzTextEdit`) updates. By contrast, the local export in `.\build\windows\PetzRendering.exe` loads all preset pets as expected.

Binary inspection of the `.pck` archives reveals that `.godot/exported/133200997/export-92f9f45a10faca2f28e1648699be99bf-Editor.scn` inside `.\bin_buggy\LnzLive-Windows-x64\windows\PetzRendering.pck` (`14,896` bytes) is `1,506` bytes smaller than the one in `.\build\windows\PetzRendering.pck` (`16,402` bytes) because **all 23 custom C# `[Signal]` connections** defined in [`src/Scenes/Editor/Editor.tscn`](../../src/Scenes/Editor/Editor.tscn) were stripped when the scene was converted to binary `.scn` during the headless CI export (`conn_count = 30` instead of `53`).

## 🔄 Steps to Reproduce
Steps to reproduce the behavior:
1. Download and extract the `LnzLive-Windows-x64` build artifact produced by GitHub Actions (available locally in `.\bin_buggy\LnzLive-Windows-x64\windows`).
2. Launch `PetzRendering.exe`.
3. Observe in the left-hand `Tree` (`FileTree`) that the **Examples** node is populated with the 21 preset `.lnz` files (`bootz.lnz`, `brownie.lnz`, `bulldog.lnz`, `snowball.lnz`, etc.).
4. Double-click any preset pet under **Examples** (e.g., `snowball.lnz`).
5. Observe that the tree item loses focus (`ReleaseFocus()`), confirming `Tree.item_activated` fired `FileTree.OnTreeItemActivated()`, but no 3D pet is generated in `PetViewContainer` and no LNZ text is loaded into `LnzTextEdit`.

## 🛑 Expected Behavior
- Double-clicking any preset pet under **Examples** in the GitHub Actions build artifact should emit `ExampleFileSelected(filepath)` and invoke both `DogGenerator.GeneratePet(filepath)` and `LnzTextEdit.OnExampleFileSelected(filepath)`, matching the behavior of the local build in `.\build\windows`.
- All 53 signal connections in [`src/Scenes/Editor/Editor.tscn`](../../src/Scenes/Editor/Editor.tscn) (both the 30 built-in Godot C++ node signals and the 23 custom C# `[Signal]` delegates) must be preserved in the exported `Editor.scn` inside `PetzRendering.pck`.

## 📋 Additional Details & Root Cause Analysis

### 1. Binary `.pck` Comparison (`Editor.scn` Stripped of All 23 Custom C# Signal Connections)
Comparing `.\build\windows` against `.\bin_buggy\LnzLive-Windows-x64\windows`:
- `PetzRendering.exe` (`109,456,896` bytes) and `data_PetzRendering_windows_x86_64/PetzRendering.dll` (`204,800` bytes) are identical in size, and both `.pck` files contain all `1,111` project files (including all `res://resources/examples/*.lnz`, `.bhd`, `.bdt`, and `.bmp` assets).
- However, `PetzRendering.pck` is `21,555,096` bytes in `.\build\windows` vs `21,553,576` bytes in `.\bin_buggy\LnzLive-Windows-x64\windows`.
- Extracting `.godot/exported/133200997/export-92f9f45a10faca2f28e1648699be99bf-Editor.scn` from both `.pck` archives shows:
  - **Local build (`.\build\windows\PetzRendering.pck`):** `16,402` bytes, `conn_count = 53` (`conns` array = `371` ints).
  - **GitHub Actions build (`.\bin_buggy\...\PetzRendering.pck`):** `14,896` bytes, `conn_count = 30` (`conns` array = `210` ints).

In [`src/Scenes/Editor/Editor.tscn`](../../src/Scenes/Editor/Editor.tscn) (lines 508–560), there are 53 `[connection ...]` entries:
- **30 connections** use built-in Godot C++ node signals (`item_activated`, `about_to_popup`, `id_pressed`, `resized`, `sort_children`, `item_selected`, `value_changed`, `toggled`, `timeout`, `pressed`, `gui_input`, `mouse_entered`, `confirmed`, `close_requested`, `index_pressed`) — **all 30 survived** in `bin_buggy`.
- **23 connections** use custom C# `[Signal]` delegates declared on [`FileTree.cs`](../../src/UI/FileTree.cs), [`DogGenerator.cs`](../../src/Rendering/DogGenerator.cs), [`LnzTextEdit.cs`](../../src/UI/LnzTextEdit.cs), and [`ToolsMenu.cs`](../../src/UI/ToolsMenu.cs) — **all 23 were stripped** from `Editor.scn` in `bin_buggy`:
  - `ExampleFileSelected` (`Tree` $\rightarrow$ `PetRoot/Node.GeneratePet` and `LnzTextEdit.OnExampleFileSelected`)
  - `UserFileSelected` (`Tree` $\rightarrow$ `PetRoot/Node.GeneratePet` and `LnzTextEdit.OnUserFileSelected`)
  - `BackupFile` (`Tree` $\rightarrow$ `LnzTextEdit.OnTreeBackupFile`)
  - `AddballDeleted`, `AnimationLoaded`, `BhdLoaded`, `BallMouseEnter`, `BallSelected`, `BallTranslationChanged`, `BallTranslationsDone` (from `PetRoot/Node`)
  - `FileBackedUp`, `FileSaved` ($\times 2$), `FindBall` (from `LnzTextEdit`)
  - `AddBall`, `ColorEntirePet`, `ColorPartPet`, `CopyLToR`, `MoveHead`, `PrintBallColors`, `Recolor` (from `ToolsMenu`)

When the user double-clicks an example pet in the left-hand tree:
1. `Tree.item_activated` (a surviving built-in C++ signal) calls [`FileTree.OnTreeItemActivated()`](../../src/UI/FileTree.cs#L69-L89).
2. `FileTree.OnTreeItemActivated()` executes `EmitSignal(SignalName.ExampleFileSelected, filepath);` (line 81).
3. Because both `ExampleFileSelected` connections were stripped from `Editor.scn`, the signal emission has no connected receivers and nothing happens.

### 2. Why Custom C# Signals Were Stripped in CI (`Release` vs `Debug` MSBuild Output Path)
In `Godot.NET.Sdk`, MSBuild outputs assemblies into `.godot/mono/temp/bin/<Configuration>/`:
- `Configuration=Debug` (the default) outputs to `src/.godot/mono/temp/bin/Debug/PetzRendering.dll`.
- `Configuration=Release` outputs to `src/.godot/mono/temp/bin/Release/PetzRendering.dll`.

When the Godot Editor starts up—including during a headless export via `fgvm export` (`godot --headless --export-release ...`)—Godot's `.NET` editor integration (`GodotSharpEditor`) loads the project's C# assembly exclusively from the **`Debug`** path:
```text
res://.godot/mono/temp/bin/Debug/PetzRendering.dll
```

In [`.github/workflows/ci-build.yml`](../../.github/workflows/ci-build.yml) (line 67) and [`.gitlab-ci.yml`](../../.gitlab-ci.yml) (line 58), the pre-export build step runs:
```powershell
dotnet build src/PetzRendering.csproj --configuration Release
```
1. On a clean GitHub Actions runner checkout where `src/.godot/` does not exist (ignored by [`src/.gitignore`](../../src/.gitignore)), running `dotnet build --configuration Release` writes `PetzRendering.dll` to `src/.godot/mono/temp/bin/Release/` and leaves `src/.godot/mono/temp/bin/Debug/PetzRendering.dll` **non-existent**.
2. When `fgvm export` launches the headless Godot editor, Godot cannot find `res://.godot/mono/temp/bin/Debug/PetzRendering.dll` while initializing the project and scanning/converting scenes.
3. Without the `Debug` assembly loaded in the editor, all C# scripts (`FileTree.cs`, `DogGenerator.cs`, `LnzTextEdit.cs`, `ToolsMenu.cs`) are treated as unloaded placeholder scripts whose custom C# `[Signal]` attributes are unknown to the editor. When Godot converts `Editor.tscn` into binary `.godot/exported/133200997/export-92f9f45a10faca2f28e1648699be99bf-Editor.scn`, it drops all 23 custom C# signal connections while keeping the 30 built-in C++ node signal connections.
4. Afterward, Godot's C# export plugin invokes `dotnet publish` for `ExportRelease` (`data_PetzRendering_windows_x86_64/PetzRendering.dll`), which succeeds with exit code `0`, masking the fact that `Editor.scn` inside `PetzRendering.pck` was serialized before the C# scripts were loaded by the editor.
5. Locally (`.\build\windows`), `src/.godot/mono/temp/bin/Debug/PetzRendering.dll` already existed from prior Godot Editor builds, so `fgvm export` loaded `PetzRendering.dll` on startup and preserved all 53 connections.

### 3. Additional Note: `Godot.NET.Sdk` Version Drift in Commit `75bc1bd`
In commit `75bc1bd`, [`src/PetzRendering.csproj`](../../src/PetzRendering.csproj) was modified from `Godot.NET.Sdk/4.7.1` to `Godot.NET.Sdk/4.8.0-dev.7` and [`src/project.godot`](../../src/project.godot) from `"4.7"` to `"4.8"`, whereas [`src/.fgvm-version`](../../src/.fgvm-version) pins `4.7.1-stable-mono`. These versions should be kept aligned (`4.7.1` / `4.7`) so CI builds using `4.7.1-stable-mono` do not encounter `GodotSharp` assembly version mismatches.

### 4. Proposed Fix Direction
1. **Build `Debug` Configuration Before `fgvm export` in CI:**
   In [`.github/workflows/ci-build.yml`](../../.github/workflows/ci-build.yml) and [`.gitlab-ci.yml`](../../.gitlab-ci.yml), change:
   ```powershell
   dotnet build src/PetzRendering.csproj --configuration Release
   ```
   to build the default `Debug` configuration expected by the Godot Editor:
   ```powershell
   dotnet build src/PetzRendering.csproj --configuration Debug
   ```
   so `src/.godot/mono/temp/bin/Debug/PetzRendering.dll` exists before `fgvm export` launches headless Godot.
2. **Keep `Godot.NET.Sdk` Synchronized with `src/.fgvm-version`:**
   Ensure [`src/PetzRendering.csproj`](../../src/PetzRendering.csproj) uses `Godot.NET.Sdk/4.7.1` and [`src/project.godot`](../../src/project.godot) uses `config/features=PackedStringArray("4.7", "C#")` to match `4.7.1-stable-mono` in [`src/.fgvm-version`](../../src/.fgvm-version).

### 5. Resolution Implemented
- Updated [`.github/workflows/ci-build.yml`](../../.github/workflows/ci-build.yml) and [`.gitlab-ci.yml`](../../.gitlab-ci.yml) to compile `src/PetzRendering.csproj` with `--configuration Debug` prior to running `fgvm export`, ensuring `src/.godot/mono/temp/bin/Debug/PetzRendering.dll` is present when the headless Godot editor initializes.
- Aligned [`src/PetzRendering.csproj`](../../src/PetzRendering.csproj) (`Godot.NET.Sdk/4.7.1`) and [`src/project.godot`](../../src/project.godot) (`"4.7"`) with [`src/.fgvm-version`](../../src/.fgvm-version) (`4.7.1-stable-mono`).
- Verified from a clean state (no pre-existing `src/.godot/` directory) that `dotnet build src/PetzRendering.csproj --configuration Debug` followed by `fgvm export` produces `Editor.scn` (`16,402` bytes) inside `PetzRendering.pck` with all 53 signal connections intact (`ExampleFileSelected` and all other custom C# `[Signal]` connections preserved).
