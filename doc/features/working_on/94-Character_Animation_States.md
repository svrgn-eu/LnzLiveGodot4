# Feature: Character Animation States & Isometric Rendering

## 📖 Overview
This feature document details the architectural approach for integrating our newly exported MagicaVoxel 8-directional isometric sprite sheets into the Godot game engine. It explains how to wire the `CharacterData` scriptable resources to the `IsoCharacter` entities to visually reflect movement and idle states across 8 directions.

## 🎯 Goals & Use Cases
- **Goal 1:** Accurately map a 2D movement vector (`Vector2`) in Godot to one of 8 discrete isometric directions (`n`, `ne`, `e`, `se`, `s`, `sw`, `w`, `nw`).
- **Goal 2:** Decouple character visual logic from the core movement logic using the `CharacterData` Resource.
- **Use Case A (Moving):** When a player commands a character to move, the character calculates its path. The visual component immediately switches to the `run_{direction}` or `walk_{direction}` animation corresponding to its trajectory.
- **Use Case B (Idle):** When the character reaches its destination and stops, it seamlessly transitions into the `idle_{direction}` state, maintaining the last direction it was facing.

## 👥 Target Audience / User Roles
- **Players:** Experience visually coherent, 8-directional isometric character movement that looks polished and matches the tactical grid.
- **Developers/Designers:** Can easily swap character visuals by just assigning a new `.tres` file (containing the 8-directional sprites) to the `CharacterData` resource in the inspector.

## ⚙️ Functional Requirements
- `[x]` **Sprite Component:** `IsoCharacter` must have a dedicated `AnimatedSprite2D` node attached to it in the scene tree.
- `[x]` **Data Driven Initialization:** Upon `_Ready()` or `OnInjected()`, `IsoCharacter` must read `Data.IsoAnimation` (the exported `.tres` SpriteFrames) and apply it to its `AnimatedSprite2D`.
- `[x]` **Angle Calculation:** During `_PhysicsProcess`, the character must calculate the angle of its current `Velocity` vector.
- `[x]` **State Machine Engine:** The character must possess a lightweight state machine to decide between base animations (e.g., `idle`, `walk`, `attack`) and append the calculated direction suffix (e.g., `_ne`). This needs to be defined in a "Direction" enum in C# which holds all eight directions. Maybe it is even a class and outputs the suffix via Method.
- `[x]` **Depth Sorting:** The `IsoCharacter` (or its sprite) must have `Y Sort Enabled` turned on to ensure characters overlap correctly in the isometric 2D perspective. The sprite `offset` must be adjusted to `(0, -32)` so the feet align with the node's origin `(0,0)`.
- `[x]` **Debug Overlay:** The state machine's active state must be visually represented above the character when the in-game debug overlay is set to "Entities".

## 🎨 UI/UX Design & Interactions
- Visually, characters will always appear to face the direction they are moving.
- Since we use 8 directions, the movement should feel fluid and responsive, preventing the "sliding sideways" look common in 4-directional isometric games.
- **Transitions:** Animations should play at a framerate matched to the character's movement speed (`Data.MovementSpeed`) for realism.

## 💻 Technical Details

### 1. The `CharacterData` Resource
The `CharacterData.cs` class already exposes the `IsoAnimation` property. This property holds the `.tres` file generated by our MagicaVoxel pipeline.
```csharp
[Export]
public SpriteFrames IsoAnimation { get; set; }
```

### 2. The `IsoCharacter` Class Updates
We need to introduce a reference to the visual sprite (located at `Visuals/CharacterSprite`), a `Direction` enum to strongly type the 8 directions, and a tracking variable for the last known direction. We also use a custom setter for the `Data` property to trigger live sprite updates in the Godot editor.

**Direction Enum Definition:**
```csharp
public enum Direction
{
    S, SW, W, NW, N, NE, E, SE
}

public static class DirectionExtensions
{
    public static string ToSuffix(this Direction dir)
    {
        return dir.ToString().ToLower();
    }
}
```

**New Fields & Editor Preview:**
```csharp
using Stateless;

private Scripts.Data.CharacterData _data;
private AnimatedSprite2D _animSprite;
private Direction _currentFacing = Direction.S; // Default direction (frontal)
private StateMachine<CharacterState, CharacterTrigger> _stateMachine;
```

**Direction Calculation Logic:**
A helper method will convert Godot's standard angles (radians) into our `Direction` enum.
*Note: Because our export pipeline explicitly maps the visual frontal view of the character to the "South" (`_s`) suffix, `Vector2(0, 1)` (which points straight down the screen) seamlessly maps to `Direction.S` without requiring confusing rotation logic in the engine.*

```csharp
private Direction GetDirectionFromVector(Vector2 direction)
{
    // Convert angle to degrees. Note: Y is down in Godot.
    float angle = Mathf.RadToDeg(direction.Angle());
    
    // Normalize to 0-360
    if (angle < 0) angle += 360f;
    
    // Map 360 degrees to 8 slices (45 degrees each)
    // 0 = E, 45 = SE, 90 = S (Frontal), 135 = SW, 180 = W, 225 = NW, 270 = N, 315 = NE
    if (angle >= 337.5f || angle < 22.5f) return Direction.E;
    if (angle >= 22.5f && angle < 67.5f) return Direction.SE;
    if (angle >= 67.5f && angle < 112.5f) return Direction.S; // Screen Down = South = Frontal View
    if (angle >= 112.5f && angle < 157.5f) return Direction.SW;
    if (angle >= 157.5f && angle < 202.5f) return Direction.W;
    if (angle >= 202.5f && angle < 247.5f) return Direction.NW;
    if (angle >= 247.5f && angle < 292.5f) return Direction.N;
    if (angle >= 292.5f && angle < 337.5f) return Direction.NE;
    
    return Direction.S; // Fallback to frontal
}
```

### 3. State Management in `_PhysicsProcess`
To handle state transitions cleanly and future-proof the character for complex actions (like attacking or flinching), we use the **[Stateless](https://github.com/dotnet-state-machine/stateless)** NuGet package.

**State & Trigger Enums:**
```csharp
public enum CharacterState { Idle, Run }
public enum CharacterTrigger { Stop, Move }
```

**State Machine Configuration (`_Ready`):**
```csharp
_stateMachine = new StateMachine<CharacterState, CharacterTrigger>(CharacterState.Idle);

_stateMachine.Configure(CharacterState.Idle)
    .OnEntry(() => PlayAnimation())
    .Permit(CharacterTrigger.Move, CharacterState.Run);

_stateMachine.Configure(CharacterState.Run)
    .OnEntry(() => PlayAnimation())
    .Permit(CharacterTrigger.Stop, CharacterState.Idle);
```

**Movement Logic (`_PhysicsProcess`):**
Instead of manually swapping strings, the physics loop simply fires triggers (`Move` or `Stop`) based on the character's velocity. The state machine handles the transition and automatically plays the correct directional animation via the `OnEntry` callback! If the direction changes while already running, the `PlayAnimation` method is called again to smoothly rotate the sprite without leaving the `Run` state.

*Note on Missing Animations:* To support testing during early asset integration, the `PlayAnimation` method includes a fallback mechanism. If a specific state animation (e.g., `run_ne`) is missing from the `SpriteFrames`, it will gracefully fall back to the `idle` animation for that direction (e.g., `idle_ne`). This ensures the character visually turns to face the correct way even if they lack walking frames.

### 4. Visual Y-Sorting & Offsets
Because Godot sorts 2D objects based on their Y-coordinate, the `CharacterBody2D` origin MUST be exactly where the character touches the ground (their feet). The MagicaVoxel exports are 64 pixels tall and are drawn centered by default (origin at waist). Therefore, the `AnimatedSprite2D` must have its `offset` set to `Vector2(0, -32)` to shift the texture up, aligning the feet perfectly with the node's Y-origin for flawless overlap calculation with obstacles and terrain.

### 5. Debug Overlay Integration
The `CurrentState` of the state machine is exposed as a public property on `IsoCharacter`. The `ScrDebugOverlay.cs` system hooks into this property and uses `DrawString` to render the active state (e.g., `Idle`, `Run`) directly above the character sprite whenever the debug level is set to "Entities" (Level 3).

- **Directional Accuracy:** Command the character to move to the top-right of the screen. Verify the `run_ne` animation plays. Command them to move straight down, verify `run_s` plays.

## 🔗 Dependencies Analysis (`CharacterData.cs`)
When implementing this feature, we must ensure we don't break existing systems that rely on `CharacterData.cs`. Current dependencies include:
1. **`IsoCharacter.cs` & `EventBus.cs`**:
   - `IsoCharacter` holds the active `CharacterData` instance (`[Export] public CharacterData Data`).
   - **Note on SpriteFrames:** The `Data.IsoAnimation` property holds a single `.tres` file (a Godot `SpriteFrames` resource). This single file is a dictionary that internally contains *all* the different animation states and directions for the character (e.g. `idle_s`, `run_se`, `walk_nw`). `IsoCharacter` simply needs to pass the string name to the `AnimatedSprite2D` component to play the correct one.
   - When a character is clicked, `IsoCharacter` emits `EventBus.Instance.CharacterSelected(Data, this)`.
   - *Impact*: None. We are only reading `Data.IsoAnimation` within `IsoCharacter`. The event signature remains unchanged.
2. **`UiCharacterPortraitTile.cs`**:
   - Subscribes to `Data.HealthChanged` to update the HUD health bar.
   - Reads `Data.PortraitAnimation` (`SpriteFrames`) to animate a 2D portrait in the UI.
   - *Impact*: None. `PortraitAnimation` is distinct from `IsoAnimation`. We intentionally keep these separated so UI portraits can be authored and animated completely independently of the in-game isometric visuals.
3. **`ScrCharacterScreen.cs`**:
   - Listens to the `CharacterSelected` event.
   - Reads `Data.Callsign`, `Data.Health`, `Data.MovementSpeed`, and `Data.Inventory`.
   - *Impact*: None. Adding `IsoAnimation` does not affect stat readouts or inventory parsing.

## 📂 File Structure Proposal
To keep assets organized, all exported MagicaVoxel 2D sprites and their associated `.tres` Godot resources should be structured by entity type and specific entity name. The export script outputs should target these specific subdirectories.

**Proposed Directory Tree:**
```text
src/
└── assets/
    └── sprites/
        ├── characters/        # Playable heroes (The Demolitionist, The Ghost, etc.)
        │   ├── DemoExport/    # Example export folder
        │   │   ├── idle.tres
        │   │   └── idle_s.png, idle_sw.png, ...
        │   └── Milena/
        ├── npcs/              # Non-hostile or dialogue entities
        ├── enemies/           # Hostile tactical units (Syndicate goons, etc.)
        └── animals/           # Wildlife or ambient creatures
```
*Note: The export pipeline (`export_pipeline.py`) naturally handles variations as subdirectories inside a given character's root folder.*
